Parte 1 · MER: Modelo Entidad-Relacion

El MER es una representacion conceptual de la base de datos: permite identificar entidades, atributos, relaciones y cardinalidades antes de escribir una sola linea de SQL. Caso de ejemplo de toda la guia: una tienda donde los clientes compran productos.

Entidad → rectangulo

Objeto del que queremos guardar informacion. Nombre en MAYUSCULAS: CLIENTE, PRODUCTO, ALUMNO, MATERIA, LIBRO.

Atributo → ovalo

Caracteristica de la entidad, dibujada arriba y conectada con una linea.

Atributo clave → ovalo subrayado

Identifica de forma unica a cada entidad. En la base se convierte en la PRIMARY KEY.

Atributo multivaluado → doble ovalo

Puede tener varios valores para la misma entidad: un cliente con dos telefonos.

Atributo derivado → ovalo punteado

Se calcula a partir de otro dato: la edad sale de la fecha de nacimiento. No se guarda.

Relacion → rombo

Accion o asociacion entre entidades: COMPRA, TIENE, CURSA, PERTENECE, REALIZA...

Cardinalidad → sobre la linea

Cuantas instancias de A se relacionan con cuantas de B: uno a uno, uno a muchos, muchos a muchos.

Ejemplo completo de MER (vertical)

Practica guiada: armá tu primer MER

Caso - La Pizzería: se registran los clientes (nombre, apellido y uno o más teléfonos) y las pizzas (nombre, precio). Un cliente pide muchas pizzas y una pizza es pedida por muchos clientes. De cada pedido interesan la fecha y la cantidad. Seguí estos pasos:

  1. Buscá las entidades: releé el texto y preguntate ¿de quién / de qué quiero guardar datos? Son cosas: clientes y pizzas. Dibujá un rectángulo para cada una.
  2. Listá los atributos: colgá de cada entidad un óvalo por característica. Cliente: nombre, apellido, teléfono. Pizza: nombre, precio.
  3. Detectá el multivaluado: ¿algún atributo con varios valores? El teléfono: usale doble óvalo.
  4. Elegí las claves: ¿qué identifica a cada uno? id_cliente e id_pizza: ovalos subrayados.
  5. Nombrá la relación: la acción que une a las entidades es pide: dibujala como rombo.
  6. Marcá la cardinalidad: releé el texto: un cliente pide muchas pizzas y una pizza es pedida por muchos clientes: es N:M. Escribí N junto al cliente y M junto a la pizza.
  7. Los datos del pedido: fecha y cantidad no son ni del cliente ni de la pizza: colgalos como óvalos del propio rombo PIDE.
Ver cómo quedaría (comparalo al terminar)

Parte 2 · DER: diagrama relacional

El DER pasa del dibujo conceptual a las tablas reales, como en MySQL Workbench: cada entidad se convierte en una caja con sus campos adentro, marcando quien es PK y quien FK. La entidad intermedia que nacio de la N:M (COMPRA) tambien es una tabla: contiene las dos claves foraneas mas sus atributos propios.

clientes

dni PK INT
nombre VARCHAR(50)
apellido VARCHAR(50)
telefono VARCHAR(20)
1──N cliente_dni

compras (intermedia)

id_compra PK AI INT
cliente_dni FK INT
producto_cod FK INT
fecha DATE
cantidad INT
N──1 producto_cod

productos

codigo PK AI INT
nombre VARCHAR(50)
precio DECIMAL(10,2)
stock INT
  • PK = PRIMARY KEY: identifica cada fila, nunca se repite ni queda vacia.
  • FK = FOREIGN KEY: apunta a la PK de otra tabla y une los datos.
  • AI = AUTO_INCREMENT: MySQL numera solo.
  • Lectura de las lineas: un cliente (1) aparece en N compras; un producto (1) aparece en N compras.
¿Con que simbolo se dibuja la entidad intermedia? En el DER se dibuja con el mismo simbolo que cualquier tabla. No tiene simbolo nuevo: la distinguen sus dos FOREIGN KEY (una hacia cada entidad que unia la N:M original) y sus atributos convertidos en columnas. Suele heredar el nombre de la relación N:M que resuelve: el rombo COMPRA pasa a ser la tabla compras.

Practica guiada: pasá ese MER a DER

Usando la pizzería del ejercicio anterior, convertí el diagrama a tablas. Seguí estos pasos:

  1. Cada entidad → una tabla: abrí una caja para clientes y otra para pizzas, con sus atributos como columnas.
  2. Las claves → PRIMARY KEY: lo que estaba subrayado (id_cliente, id_pizza) ahora se marca como PK.
  3. ¿Cómo era la relación? PIDE era N:M: en el DER esa relación se convierte en una tercera tabla intermedia: pedidos.
  4. Dentro de la intermedia: su PK (id_pedido) y las dos FK (id_cliente hacia clientes, id_pizza hacia pizzas).
  5. Los atributos del rombo → columnas: fecha y cantidad colgaban del rombo PIDE: ahora son columnas de pedidos.
  6. Elegí los tipos de dato: INT para ids y cantidad, VARCHAR para textos, DECIMAL(10,2) para precio, DATE para fecha.
  7. Chequeo final: ¿quedan 3 tablas? ¿cada una tiene PK? ¿las dos FK de pedidos apuntan a PK existentes?

Nota: el teléfono multivaluado queda simplificado en una columna; si necesitáramos varios por cliente, tendría tabla propia.

Parte 3 · BD: creacion en MySQL

Paso 1: crear la base de datos

Una base de datos es la carpeta logica que agrupa las tablas del sistema. Se crea una sola vez; USE indica con cual trabajamos:

-- Crea la base (si no existe) y entra en ella
CREATE DATABASE IF NOT EXISTS tiendita;
USE tiendita;

Paso 2: crear una tabla

Cada entidad del diagrama se convierte en una tabla. Entre parentesis se listan las columnas: NOMBRE, TIPO y restricciones, separadas por comas (la ultima sin coma):

CREATE TABLE clientes (
    dni     INT,
    nombre  VARCHAR(50),
    precio  DECIMAL(10,2),
    fecha   DATE,
    PRIMARY KEY (dni)
);
TipoPara que sirveEjemplo
INTNumeros enterosdni, stock, cantidad
DECIMAL(10,2)Decimales exactosprecio
VARCHAR(n)Texto corto variablenombre, telefono
DATEFecha AAAA-MM-DDfecha_nacimiento

  • PRIMARY KEY: identifica cada fila.
  • NOT NULL: obliga a cargar siempre ese dato.
  • FOREIGN KEY ... REFERENCES: conecta con la PK de otra tabla.

Script completo: base TIENDITA

Guardalo como tiendita.sql: crea la base, las tres tablas, carga datos de prueba y arma la boleta con un JOIN.

CREATE DATABASE IF NOT EXISTS tiendita;
USE tiendita;

CREATE TABLE clientes (
    dni INT PRIMARY KEY,
    nombre VARCHAR(50) NOT NULL,
    apellido VARCHAR(50) NOT NULL,
    telefono VARCHAR(20)
);

CREATE TABLE productos (
    codigo INT AUTO_INCREMENT PRIMARY KEY,
    nombre VARCHAR(50) NOT NULL,
    precio DECIMAL(10,2) NOT NULL,
    stock INT NOT NULL DEFAULT 0
);

-- Entidad intermedia COMPRA (resuelve la N:M) -> tabla compras
CREATE TABLE compras (
    id_compra INT AUTO_INCREMENT PRIMARY KEY,
    cliente_dni INT NOT NULL,
    producto_codigo INT NOT NULL,
    fecha DATE NOT NULL,
    cantidad INT NOT NULL,
    FOREIGN KEY (cliente_dni) REFERENCES clientes(dni),
    FOREIGN KEY (producto_codigo) REFERENCES productos(codigo)
);

INSERT INTO clientes VALUES
    (30111222, 'Ana',  'Gomez', '2664-111111'),
    (28333444, 'Luis', 'Perez', '2664-222222');

INSERT INTO productos (nombre, precio, stock) VALUES
    ('Teclado', 8500.00, 10),
    ('Mouse',   4200.50, 15);

INSERT INTO compras (cliente_dni, producto_codigo, fecha, cantidad) VALUES
    (30111222, 1, '2026-08-20', 2),
    (30111222, 2, '2026-08-21', 1),
    (28333444, 1, '2026-08-21', 3);

SELECT c.apellido, p.nombre, co.fecha, co.cantidad,
       p.precio * co.cantidad AS total
FROM compras co
JOIN clientes  c ON c.dni    = co.cliente_dni
JOIN productos p ON p.codigo = co.producto_codigo;

Como probarlo

  • Abrir phpMyAdmin o MySQL Workbench.
  • Pegar el script completo y ejecutarlo.
  • Verificar las tablas clientes, productos y compras.
  • Ejecutar solo el SELECT final: muestra la boleta con el total.
  • Prueba extra: insertar una compra con cliente_dni inexistente debe fallar; la FOREIGN KEY protege los datos.

Extra · Dibujar con el programa Dia

Dia es un programa libre y gratuito para hacer diagramas (alternativa a Visio). Sirve para pasar el MER y el DER a la compu antes de entregarlos.

Instalacion

  • Windows: bajar el instalador desde www.dia-installer.de (sección Download).
  • Linux: sudo apt install dia

La pantalla

  • Lienzo central: donde se arma el diagrama.
  • Paleta izquierda: figuras de una coleccion llamada HOJA. El desplegable de arriba cambia de hoja.
  • Clic en una figura y luego clic en el lienzo para colocarla; doble clic para escribir su nombre.
Lo que queres dibujarHoja y figura en Dia
Entidad (rectangulo)Hoja ER → Entity
Relacion (rombo)Hoja ER → Relationship
Atributo (ovalo)Hoja ER → Attribute
Tablas del DER (PK/FK)Hoja Database → Table + Reference

Trucos

  • Unir figuras: herramienta LINEA desde un borde hasta otro; quedan pegadas y siguen unidas al moverlas.
  • Cardinalidades: herramienta TEXTO (T) y escribir 1:N o N:M junto a la linea.
  • En la tabla (hoja Database), doble clic abre el editor de columnas: nombre, tipo y tilde PRIMARY KEY.
  • Archivo > Guardar deja el .dia editable; Archivo > Exportar genera el PNG/PDF para entregar.
  • Atajos: Ctrl+rueda zoom, Ctrl+D duplicar, Supr borrar, Ctrl+Z deshacer.

Parte 4 · Ejercicios

Resolvé cada ejercicio siguiendo siempre los mismos pasos: a) MER en papel o con el programa Dia · b) DER con las tablas, PK y FK · c) script .sql probado en phpMyAdmin o Workbench · d) todo guardado en la carpeta con tu apellido.

Ejercicio 1 - La Biblioteca

De cada LECTOR: nombre, apellido y uno o VARIOS telefonos (multivaluado). De cada LIBRO: titulo, autor y anio. Un lector presta MUCHOS libros y un libro es prestado por MUCHOS lectores (N:M). De cada prestamo: fecha_prestamo y fecha_devolucion (iran en la entidad intermedia).

Preguntas: cuantas entidades hay? Que relacion las une y con que cardinalidad? Donde aparece un atributo multivaluado?
Entrega: MER dibujado + DER + biblioteca.sql con datos de prueba y una consulta JOIN.

Ejercicio 2 - La Veterinaria

De cada DUENO: nombre, fecha_nacimiento y varios telefonos (multivaluado). La EDAD no se guarda: se calcula (derivado). De cada MASCOTA: nombre y especie. Un dueno tiene MUCHAS mascotas pero cada una pertenece a UN dueno (relacion 1:N). Pensa donde va la FK.

Atencion: al ser 1:N no hace falta tabla intermedia.
Entrega: MER + DER + veterinaria.sql + consulta JOIN que muestre mascota, dueno y edad calculada.

Ejercicio 3 - La Escuela (espejo del Boletin Digital)

ALUMNO (dni clave, nombre, apellido) y MATERIA (id, nombre). Un alumno cursa MUCHAS materias y una materia MUCHOS alumnos (N:M). De cada cursada: nota_1co y nota_2co; el promedio se calcula. Comparalo con tu base bdescuela.

Extra: en tu boletin el promedio se guardaba en nota_final. Que diferencia hay con tratarlo como atributo derivado?
Entrega: MER + DER + escuela_der.sql + consulta JOIN tipo boletin.
